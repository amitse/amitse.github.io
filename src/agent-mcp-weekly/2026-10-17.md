## MCP: model workflows meet a stateful application

The week’s most interesting MCP artifact is [mcp-for-blender-pro](https://github.com/anujasid/mcp-for-blender-pro), a repository created October 15 that combines an authenticated Streamable HTTP MCP server with 21 scene tools. Its companion workspace exposes scene objects, viewport snapshots, approvals, and a task board; its tools cover creating, inspecting, editing, capturing, asset search, Blender API consultation, and scene export.

The important design decision is not the long roster of supported model providers. It is that the project serializes work: tasks run sequentially “so scene edits stay ordered,” a blocked task gets one correction attempt, and a second failed review stops the workflow. A manager turns a request into assignments and acceptance criteria, workers operate on the scene, and reviewers approve or return findings. That is a much more credible use of an agent team than concurrent edits to the same scene graph, which would merely turn coordination into an ordering bug.

A 3D scene gives review something concrete to inspect: object structure, materials, snapshots, and exported artifacts. This is where MCP is at its best. The server’s verbs describe durable application state rather than asking a model to manipulate a GUI through pixels; review is attached to the resulting artifact, not to the model’s explanation of what it believes it changed. The repository is very new, so it is an architectural example rather than evidence of production maturity. Still, its boundaries are worth borrowing: semantic tools, one ordered mutation path, visible review state, and a bounded correction loop.

## Frameworks: resumption becomes runtime semantics

[LangGraph 1.2.16](https://github.com/langchain-ai/langgraph/releases/tag/1.2.16), published October 16, is nominally a maintenance release, but its fixes describe exactly where long-running agent systems fail. The release lets other tasks finish when a resume value is invalid; applies a resumed `Command` update once; stops a subgraph from rerunning completed tasks on resume; saves a resumed exit run’s pending writes once; and adds `prune` to the Postgres checkpoint savers.

Those are not glamorous changes. They are more important than glamorous changes. Resuming a workflow is not rerunning a prompt with old messages attached; it is recovery against an execution history. A runtime that repeats a completed side effect, drops a pending write, or lets malformed human input halt unrelated work is not durable enough for consequential automation. The release is a compact checklist for the bugs that appear when resumption is treated as a UI convenience rather than a correctness property.

[CrewAI 1.15.28](https://github.com/crewAIInc/crewAI/releases/tag/1.15.28), published October 14, addresses the same gap from the operator’s side. It adds `crewai eval`, which reports where a stopped model broke. Its flow fixes learn from resumed human feedback and preserve reviewed output types; the release also preserves native tool aborts and post-hook cache identity, and emits completed-call events for streamed Anthropic tool calls.

The phrase “where a stopped model broke” is the useful one. A retry loop does not make an agent operable. A failed run must leave a useful causal trail: the state that existed, the invocation that stopped, the human input that changed the path, and the output that passed or failed review. LangGraph is tightening replay and write semantics; CrewAI is making failures and resumed state more legible. Both directions matter more than a new persona abstraction.

## Evidence, not narration

Hacker News supplied a useful real-time measure of developer interest in this production question. At verification, Anthropic’s account of [how the Claude Code team does code review](https://news.ycombinator.com/) was at **250 points and 232 comments**. The unusually high comment-to-point ratio fits the topic: developers do not need another demonstration that a model can write a patch; they need a review process that can distinguish an attractive diff from a safe change.

The architecture to aim for is “agent as participant in an evidence-producing development loop,” not “agent as author.” A review agent should identify the relevant change, state a testable hypothesis, run scoped checks, attach their outputs, and leave the final acceptance decision legible to a human reviewer. Review is not a ceremonial model critique after code is written. It is where an organization specifies what counts as evidence, stops risky effects, and turns a discovered failure into a future test.

Anthropic’s [reconstruction of the origins of the NIST ECDSA curve seeds](https://www.anthropic.com/research/ecdsa-curve-origins), published October 16, shows the same distinction in research. The linked story was at **701 points and 274 comments** on Hacker News when checked. Anthropic reports that, in under half an hour, Claude found that the standardized P-192, P-224, P-256, P-384, and P-521 seeds were outputs of the C library’s `lrand48` generator, seeded with Unix timestamps—not hashes. The work did not stop at a fluent answer: it used a scanner over 34 generator/output-slice combinations and provides a reproduction method. Anthropic explicitly cautions that this is “not a cryptographic break, new attack, or weakness in the ECDSA curves.”

That bounded conclusion is part of what makes the example valuable. An agent’s useful contribution is not confidence in an obscure mechanism; it is an executable, compact investigation that other people can test. In code review that bundle is a diff, scoped tests, and observable tool output. In research it is a method and a reproduction path. Agent systems should optimize for those artifacts, not for longer narrated reasoning.

## What to watch next week

Take one workflow that currently “resumes” after human interruption and write a failure test for it. Start two independent tasks, then supply a deliberately invalid resume payload. Verify that unaffected work finishes; completed side effects do not repeat; a corrective state update happens exactly once; and the checkpoint or event history identifies the rejected payload and its task.

This is deliberately narrower than adopting a new framework. If a system cannot pass that test, more planning agents will make it more eloquent, not more reliable. The LangGraph fixes provide a concrete starting checklist, while the Blender project offers a useful interface pattern: expose the artifact, the attempted work, and the review finding instead of hiding the run behind a chat transcript.

## TL;DR

The meaningful agent work this week was operational rather than theatrical. LangGraph tightened resume behavior across tasks, subgraphs, writes, and checkpoints, while CrewAI added failure-localizing evaluation and better preservation of reviewed, resumed state.
