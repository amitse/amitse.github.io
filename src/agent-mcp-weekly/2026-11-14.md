# 🔌 AI Agent & MCP Weekly — Week of 9 November 2026

## Highlights

The dominant signal this week is that agent builders are treating the control plane as a distinct product. The consequential releases are not asking language models to narrate better plans; they add bounded decision layers, durable workflow state, and feedback loops around the generative model. That is a healthier direction: the model can propose and act, but the system needs fast mechanisms to decide, verify, resume, and escalate.

## MCP protocol and servers

Nothing shipped in the MCP specification itself during the week. That is useful context rather than a gap: the protocol is increasingly infrastructure, while the consequential work is moving into systems that decide whether a tool should run, preserve state when a workflow stops, and expose an agent to an operational environment.

Google’s new [Gemini Decisions API](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/) makes that shift unusually explicit. Google describes tool selection, policy checks, model routing, and context grading as its intended uses. Gemini Decision 1 can evaluate up to 1,000 bounded questions against a shared multimodal input, returning option probabilities and confidence scores rather than generating prose token by token. Google reports 50–100 ms median model compute, 150–250 ms end-to-end latency, and $0.10 per million input tokens with no billed output tokens.

The architectural implication is substantial. A tool-using agent should not make an expensive, open-ended generation call just to answer “may I call this tool?”, “which handler applies?”, or “is this evidence sufficient?” Google also says Search uses the Decisions API as a safety layer for MCP tools to detect adversarial behavior and content. That is the right framing for MCP safety: a tool boundary needs a fast, separately inspectable gate—not merely another instruction inside the context window of the agent proposing the action. A confidence score also creates a principled handoff point to a stronger model, an alternate verifier, or a human.

## Agent frameworks

[LangGraph 1.2.21](https://github.com/langchain-ai/langgraph/releases/tag/1.2.21), released November 12, is a maintenance release whose fixes identify real production pressure. It corrects how `get_subgraphs` matches namespace segments, permits an undeclared subgraph namespace to be read with its parent graph, and documents that each `interrupt()` call has its own identifier in `UnknownInterruptError`. None of that makes for a launch video, but it is the anatomy of a mature orchestration runtime: nested graphs, partial visibility, and multiple outstanding interruptions are semantics, not incidental implementation details.

Making an interruption’s identity and scope explicit is a design decision with operational consequences. Once a human approval or external wait state can be conflated with another, a long-running workflow becomes unsafe to resume. Frameworks that model these states as first-class data can recover deterministically; frameworks that leave them as conversational history eventually force an operator to guess what the agent meant.

[CrewAI 1.15.40](https://github.com/crewAIInc/crewAI/releases/tag/1.15.40) and [1.15.41](https://github.com/crewAIInc/crewAI/releases/tag/1.15.41), released November 11 and 12, press on the same wound from a different direction. Version 1.15.40 adds exact historical-state lookup by row ID, backend record-lifecycle and pagination tests, scaffolding standalone agents as JSON by default, and async execution of `after_llm_call` hooks. Version 1.15.41 supports approved private URL hosts and preserves earlier step outputs when a run resumes after human feedback.

Keeping earlier step outputs across a human-feedback resume sounds mundane. It is not: a human checkpoint without durable prior outputs is a partial reset disguised as collaboration. Together with historical lookup, it suggests a framework transition from agents as ephemeral chats to agents as records with an auditable lifecycle. The private-host control is the other half of the same maturity move. An agent runtime is an authority boundary, and fetching a URL is not intrinsically harmless merely because it looks like a read.

## Agentic patterns and architectures

Simon Willison’s account of building [Beep Locator](https://simonwillison.net/2026/Nov/9/mysterious-beeps/) is this week’s best concrete lesson in agent architecture. The project used a Python coordinator, WebSockets, and spare devices acting as browser-based microphones to triangulate an intermittent beep. It located the source to within about 40 cm: an old carbon-monoxide detector in a pile of boxes.

The agent was not asked to “reason harder” about a sound it could not hear. It was given an instrumented environment: 60-second audio buffers, a detection algorithm, timestamped observations, replay controls, test claps, and multiple listeners whose locations could be adjusted. Willison’s conclusion is apt: *“Figuring out ways to let coding agents perceive the world around them is a whole lot of fun.”* The more important point is that perception came from software adapters and observable state, while verification came from replaying recorded clips and testing known claps.

The implementation also has a sharp security lesson. To support unattended iteration, the listeners had an `installModule()` capability through which the coordinating server could execute fresh code on browser clients without manually refreshing each device. In a one-off controlled experiment, that avoided repeated microphone-permission prompts. In a general-purpose agent platform, it is remote code execution. The same mechanism that gives an agent “ears” can grant unacceptable authority. Deployment, tool scope, and user consent must be explicit runtime contracts, not assumed properties of an integration.

The week’s cross-story connection is unusually clean. Google’s Decisions API supplies a cheap, calibrated control-plane primitive for choosing and gating actions. LangGraph and CrewAI make interrupted execution and historical state durable. Beep Locator supplies the feedback surface that lets an agent test whether its actions worked. The useful unit is not simply “a smarter agent,” but a system with separate lanes for generation, decision, execution, observation, and recovery.

## Notable projects and demos

Beep Locator is worth reading because it closes a physical feedback loop rather than merely generating an artifact. Its calibration scheme was imperfect, so the interface exposed a “Rough mode” for human-estimated device positions before refining them from sound. That is excellent human-in-the-loop design: the human supplies a low-precision fact cheaply, and the system performs repetitive measurement and inference.

The project makes verification visible. Claps appear differently from beeps, recordings can be replayed device by device, and a user explicitly marks the target sound before the system classifies future events. These interface choices avoid the common agent failure mode of silently optimizing an unverified proxy. Builders working on browser agents, robotics-adjacent tools, or operational automation should add an inexpensive observable test before giving an agent freedom to make consequential changes.

Anthropic’s [Claude Fable 5.2 and Mythos 5.2 release](https://www.anthropic.com/claude-fable-and-mythos-5-2), dated November 9, reinforces why those harnesses matter. Anthropic positions Fable as an advisor to smaller models and as an orchestrator that delegates simpler tasks. In the company’s published evaluation table, Fable 5.2 scores 49.1% on FrontierCode 2.0 at Xhigh effort, versus 45.5% for Opus 5.5; Anthropic also says Fable can approximately match Opus 5.5’s top score at high effort for roughly half the cost per task.

Those are vendor-published benchmarks, not independent proof, and should be read accordingly. The architecture is nevertheless meaningful: use an expensive model where ambiguity and coordination dominate, then delegate constrained work to cheaper workers. The limiting factor is no longer only whether a model can generate code; it is whether the surrounding runtime can bound, observe, evaluate, and safely resume delegated actions.

## What to try next week

Add a separate decision gate before your agent’s highest-risk tool call this week. Start with one action—sending an external message, modifying production data, or invoking a browser with authenticated state—and define a closed set of outcomes: allow, deny, request clarification, or escalate. Feed the gate the proposed action, the relevant policy, and a concise evidence bundle; log the returned confidence alongside the eventual result.

Do not bury this in the agent’s system prompt. Make it a runtime step with a schema, a threshold, and an audit record. Even if you use a conventional classifier or rules engine rather than Gemini Decisions, you will learn where your agent’s actual authority boundary is—and that is usually more valuable than another week of prompt tuning.

## TL;DR

This week was about agent control planes. Google’s Decisions API makes bounded, calibrated choices cheap enough to sit in front of routing, policy, and tool-use decisions, including MCP safety checks. LangGraph and CrewAI concentrated on the unglamorous but essential mechanics of scoped interruptions, state history, and resuming after human feedback. Simon Willison’s Beep Locator showed the complementary pattern: give an agent observable sensors and a testable feedback loop instead of asking it to infer the world from prose. Better models will expand what agents can attempt, but production systems will be differentiated by how explicitly they control authority, state, and evidence.
