## 🔌 MCP Protocol & Servers

No new MCP specification releases dropped this week. The most architecturally interesting MCP signal is structural: GitHub has now added an "MCP Registry" entry directly in their global platform navigation bar, labeled **New** and described as "Integrate external tools." It sits alongside Copilot and Actions as a first-class platform feature, not a developer preview buried in docs. This is GitHub publicly committing to MCP as the integration layer for its agentic platform — not just supporting it, but owning the discovery surface. When the registry lives in the top-level nav of the largest code host, the question of whether MCP becomes the dominant tool protocol has effectively been answered. The question now is who controls curation and what that gatekeeping looks like.

The other MCP-adjacent story this week is OpenAI's Lockdown Mode going live, noted by Simon Willison on June 5. The design directly addresses what Willison calls the "Lethal Trifecta": a system that simultaneously has access to private data, exposure to untrusted content, and a mechanism for data exfiltration. This isn't a hypothetical threat model for agents — it's a description of exactly what happens when an MCP-connected agent processes incoming email or reads a document from an untrusted source. Lockdown Mode is currently limited to personal ChatGPT accounts, but the architecture it describes (restricting tool calls and external connections based on context) is the kind of thing that will need to exist at the MCP protocol level eventually, not just in individual hosts.

## 🤖 Agent Frameworks

[LangGraph's](https://github.com/langchain-ai/langgraph/releases/tag/1.2.3) most significant work this week wasn't a new capability — it was infrastructure. Versions [1.2.3](https://github.com/langchain-ai/langgraph/releases/tag/1.2.3) (June 1) and [1.2.4](https://github.com/langchain-ai/langgraph/releases/tag/1.2.4) (June 2) landed alongside a major SDK overhaul that rewrote the streaming stack. The SDK now supports WebSocket transport alongside SSE, adds v3 streaming support to RemoteGraph, and introduces projection interleaving — a mechanism for combining message streams from multiple concurrent subagents into a coherent output stream. A specific tell: `ProtocolEvent.eventId` was renamed to `event_id` to match the wire format — the kind of fix that happens when you're actually running things in production and the field names stop mattering.

The architectural decision embedded in all this is: long-running agents are a streaming problem, not a completion problem. The existing mental model of "call the API, get a response" breaks down when an agent runs for 30 minutes across a multi-step workflow. You need resilient streams, reconnect logic, and a way to observe what's happening in nested subgraphs without blocking on their completion. LangGraph is building that transport layer, which most people building agents have been handwaving over.

[CrewAI](https://github.com/crewAIInc/crewAI/releases/tag/1.14.7a1) shipped two alpha releases this week — [1.14.7a1](https://github.com/crewAIInc/crewAI/releases/tag/1.14.7a1) on June 3 and [1.14.7a2](https://github.com/crewAIInc/crewAI/releases/tag/1.14.7a2) on June 5 — and the interesting story isn't the individual features but what the refactoring reveals. They split `flow.py`, their main orchestration monolith, into three focused modules: DSL (the decorator-based flow definition syntax), definition (the `FlowDefinition` data structure built from that metadata), and runtime (execution). The a2 release adds a full chat API for conversational flows with `handle_turn`, and surfaces `finish_reason`, `response.id`, and sampling parameters as first-class events in the LLM trace.

The DSL-to-definition-to-runtime separation is a mature architectural move. It means the same flow definition can be introspected, serialized, or deployed differently without touching the runtime. The `FlowDefinition` type is the object that reasoning systems or orchestration layers can inspect without executing. This matters if you want to compare two flow versions, run a flow partially in simulation, or expose flow metadata to an observability system. The monolith couldn't do any of that cleanly. The addition of `finish_reason` and `response.id` surfacing is worth noting separately: you can't build reliable agent recovery logic without knowing why the LLM stopped, and you can't correlate traces without stable response IDs.

AutoGen had no releases this week — last release (python-v0.7.5) was September 30, 2025.

## 🏗️ Agentic Patterns & Architectures

The most discussed infrastructure project on Hacker News this week with direct relevance to agents was [pg_durable](https://github.com/microsoft/pg_durable), Microsoft's open-sourced library for in-database durable execution on PostgreSQL (314 points, 77 comments). The core idea: long-running workflows, retry logic, and durable task state live inside the database as SQL-native primitives rather than in an external workflow engine. For agents, this matters because agent workflows are inherently stateful — they pause waiting for tool results, resume on callback, potentially run for hours, and need to survive process restarts without losing work.

The architectural argument pg_durable makes is that you already trust your database with your critical state; adding workflow durability there is less operational complexity than deploying a separate orchestration service (Temporal, Airflow, Step Functions). Whether that's the right tradeoff depends on your infrastructure, but the fact that Microsoft is building this is a signal that agent workflow persistence is moving from "figure it out yourself" territory into a solved-problem space.

The [lowfat](https://github.com/zdk/lowfat) project (109 points, 56 comments on HN) represents something architecturally different: not durability infrastructure, but the other half of the token cost problem — the noise that goes *into* the agent. Author `zdkaster` reported 91.8% token reduction across 4.4M raw tokens over two months of personal use, with per-command breakdowns that hold up under scrutiny: `kubectl get` at 93.9%, `grep` at 96.2%, `docker` at 96.1%. Those numbers are extreme but plausible because CLI tools are designed for humans who can visually skip ANSI color codes, progress spinners, deprecation warnings, and column-aligned headers. An LLM can't skip any of it — every character costs.

The design is a Rust binary that sits between any CLI command and the agent consuming its output. Architecturally it runs three filter layers in sequence: a library of built-in processors (strip-ansi, dedup-blank, token-budget, redact-secrets), a declarative `.lf` DSL for per-command rules (bundled plugins for git, kubectl, docker, grep, find), and Python or shell escape hatches for logic the DSL can't express. Intensity is adjustable: `lite` preserves most context, `full` is the default balance, `ultra` maximizes compression. Integration with Claude Code is a single PreToolUse hook entry in `.claude/settings.json` — lowfat intercepts every Bash call before the output reaches the model. The author describes it as local-first, no telemetry, composable via UNIX pipes, and intentionally extensible: bundled plugins cover the common cases, but private or enterprise CLIs require user-owned filters that no public tool can ship.

The HN thread raised the honest objection: does token reduction come at a quality cost? One highly-upvoted comment argued there's no benchmark showing savings don't degrade agent reasoning. A commenter cited VS Code's own context-trimming feature (launched in v1_121) as evidence the approach works in production. The most pointed concern: some users reported that comparable tools (rtk, lean-ctx) "confuse the agent more than help" — if the agent tries to work around the filter and makes more tool calls than it would have otherwise, the savings evaporate. lowfat's answer to this is adjustable aggressiveness and user-owned plugins: you stay in control of what gets stripped.

The complementary story this week came from the output side. [Caveman](https://github.com/JuliusBrussee/caveman) by Julius Brussee — described as "why use many token when few token do trick" — reached 69,300 GitHub stars in roughly two months, making it one of the fastest-growing prompt engineering repositories ever. It's not a CLI tool; it's an agent skill that installs into Claude Code, Codex, Cursor, Windsurf, Cline, and 30+ other coding agents, instructing the LLM to drop preamble, hedging, and polished prose while preserving 100% of technical substance. Brussee's before/after is direct: a 69-token explanation of React re-render behavior becomes 19 tokens in caveman mode. The claimed ~65% output reduction across benchmarked tasks matters because agent outputs are re-loaded as input context on the next turn — output verbosity compounds through a session.

The benchmark controversy is worth knowing. Max Taylor ran a 5-arm eval across 24 prompts: baseline, "be brief.", and caveman lite/full/ultra. Quality scores were within 1.5% of each other across all arms. Token counts were nearly identical between "be brief." (419 mean tokens) and caveman full (404). The honest read: "be brief." matches caveman on both quality and compression in a single-session eval. Where caveman earns its keep is session persistence — skill files are durable across sessions, "be brief." gets forgotten — and in the structured intensity dial (lite/full/ultra) that lets users tune without rewriting instructions. Brussee also shipped `caveman-shrink`, an MCP middleware that compresses tool descriptions before they enter the context window, and `cavegemma`, a Gemma 4 31B fine-tune trained on before/after pairs, which is the more interesting long-term bet: baking the compression into weights rather than prompts.

Read lowfat and caveman together and the pattern is clear. lowfat filters CLI noise on the way in; caveman compresses agent prose on the way out. Both are working around a design gap: standard CLI tools weren't built for LLM consumers, and LLMs weren't trained to be economical with output tokens when nobody was counting. Deepgram's `dg` CLI, also released in April, added a third approach: auto-detecting when it's running inside an agent environment (via environment fingerprints) and switching output format automatically to structured, machine-readable data. That's the direction where this ends up — CLIs that know their consumer is an agent and behave accordingly, rather than requiring a filter layer in between.

A quieter signal this week: Jason Swett's post on building a [TDD skill for coding agents](https://www.saturnci.com/my-agent-skill-for-test-driven-development.html) (129 points, 51 comments) generated substantive discussion. The pattern — writing compact, loadable skill documents that teach agents domain-specific workflows — is becoming standard practice among people who build agents professionally. The interesting design choice is what belongs in a skill file versus what belongs in a system prompt: skills are reusable, portable, and loaded on demand; system prompts are always-on context. Keeping them separate is the same separation LangGraph makes between agent configuration and task configuration.

## 🧪 Notable Projects & Demos

The HN post "Did Claude increase bugs in rsync?" (298 points, 294 comments) is worth noting not for its conclusion but for what the discussion revealed. The analysis looked at bug commit rates in rsync before and after AI-assisted development became common. The thread became a proxy debate for the broader question of coding agent quality at the commit level. The substantive finding from the discussion: most people who've actually read agent transcripts at scale agree that agents introduce a specific class of subtle bug — correct-looking changes that fail in edge cases — that's harder to catch in code review than obvious errors. This is the right thing to be studying, and the community is starting to gather actual data rather than anecdote.

## 📡 Industry Moves

Simon Willison's write-up on June 3 of Uber's decision to cap AI tool usage at $1,500 per month per tool contains the most useful cost data point of the week. From the Bloomberg article Willison cited: "The rideshare giant is limiting all employees to $1,500 in monthly token spending per AI coding tool." Willison notes: *"If we assume two actively used tools per engineer that's $3,000 * 12 = $36,000 cap per engineer per year. Levels.fyi lists the median yearly compensation package for Uber software engineers in the USA at $330,000."* The cap isn't a retreat from AI adoption — it's a rational policy response to Uber blowing its entire 2026 AI budget in four months because nobody had predicted how fast token-burning coding agents would be adopted.

This is the organizational context that makes lowfat and caveman's timing relevant. Individual developers can absorb verbose CLI output and waffle-heavy agent responses. Engineering orgs at Uber's scale cannot — and when your engineers are running `kubectl get pods` 100 times a day through an agent, 93.9% per-call token savings is not a novelty project. It's budget management.

Microsoft's MAI model announcements (June 2, noted by Willison) are relevant context: MAI-Thinking-1 at 1T parameters / 35B active for reasoning tasks, and MAI-Code-1-Flash at 137B parameters / 5B active rolling out to GitHub Copilot users in VS Code. The MoE architecture on both models reflects the same cost-performance tradeoff Uber is navigating: you want reasoning quality without paying full dense-model inference costs on every token.

## 💡 One Thing to Try

Install lowfat's shell integration (`eval "$(lowfat shell-init zsh)"`) for a week and run `lowfat history` at the end. The history command ranks every command you invoked by `cost = runs × avg_tokens × (1 − savings)` — it shows you exactly where agent token spend is concentrated in your workflow, ranked by potential impact. Most people find one or two commands (usually something like `grep` or `kubectl`) dominating the distribution. That's the place to write a custom `.lf` plugin. The result isn't just cost reduction — it's understanding which parts of your CLI environment are producing the most noise for the agent, which turns out to be a different question than which commands you run most often.

## 📊 TL;DR

This week's dominant signal is the collision between agent capability and agent economics. LangGraph's streaming overhaul and CrewAI's flow architecture refactor are both investments in production durability — the infrastructure you need when agents run for minutes, not seconds. At the same time, Uber's $1,500/month cap brings the token cost question from abstract to concrete. lowfat and caveman address it from opposite ends of the conversation: lowfat strips CLI noise before it enters the context window (91.8% reduction in the author's real usage), caveman compresses agent output before it compounds across session turns (~65% on verbose responses). Neither is a complete solution — lowfat risks agent disorientation if stripping is too aggressive, caveman is functionally matched by "be brief." in single-session evals — but together they're defining the emerging design surface: the agent-aware CLI. The next version of this isn't a filter layer; it's CLIs that detect their consumer is an agent and behave accordingly. Microsoft open-sourcing pg_durable is the clearest indicator yet that agent workflow persistence is becoming infrastructure, not a DIY problem.
