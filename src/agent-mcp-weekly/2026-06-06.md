## The CLI as an Agent Surface

There's a class of bug that's hard to see until you've run a few hundred agent tasks and started reading the transcripts. The agent calls a CLI tool. The tool prints a nicely aligned table with truncated columns, ANSI color codes, and a progress spinner. The agent gets back a wall of escape sequences and partial data, burns two more tool calls trying to extract the ID it needed, makes an assumption, and either gets it wrong or succeeds despite itself. Nobody filed a bug. The CLI "worked."

This is the central problem with building CLI tools in 2026: the design assumptions baked into most of them — pretty tables, interactive prompts, helpful confirmations — are exactly what breaks agents. The same output that a human finds readable is noise to an agent. The same safety rails that protect a human from mistakes block an agent from finishing its task.

HuggingFace published a detailed writeup this week about how they redesigned their `hf` CLI to serve agents as a first-class audience alongside humans. The results were concrete enough to be useful: 94% task success rate with the agent-optimised CLI versus 84% with raw HTTP/SDK, and between 1.3× and 6× token reduction depending on task complexity. That's not a minor tweak. That's a different tool.

What they documented is a set of design decisions that compound. None of them is complicated. Taken together, they define what it means to build a CLI surface that agents can actually use.

---

## Two Audiences, One Binary

The foundational tension is that a CLI serves a terminal — a human eye looking at a screen — and also serves a subprocess call from a program that will read stdout as raw bytes. These two consumers want almost opposite things.

Consider a fictional CLI called `depot` — an artifact and package registry management tool for developer teams. A developer running `depot artifacts list --registry prod` wants something like this:

```
NAME                         VERSION    SIZE     UPDATED
─────────────────────────────────────────────────────────
api-service-linux-amd64      2.4.1      42.3 MB  3 days ago
worker-linux-amd64           2.4.0      38.1 MB  5 days ago
frontend-static              1.9.2      8.4 MB   today
```

That output is correct for a human. It's useless for an agent. The dates are relative and unparseable. The size units are formatted for reading, not for comparison. The column alignment and decorative divider line are noise. If the artifact name is longer than the column, it gets truncated — silently dropping data the agent might need.

The same command in agent mode should produce this:

```
api-service-linux-amd64	2.4.1	44367872	2026-06-03T09:22:14+00:00	prod
worker-linux-amd64	2.4.0	39977984	2026-06-01T14:05:31+00:00	prod
frontend-static	1.9.2	8808448	2026-06-06T00:01:09+00:00	prod
```

Tab-separated. Full names. Byte counts instead of formatted sizes. ISO 8601 timestamps. No ANSI codes. Nothing truncated.

The right implementation is not two separate commands or a `--format tsv` flag the agent has to know about in advance. The right implementation is auto-detection. When the process runs inside a known agent harness — detected via environment variables like `CLAUDECODE`, `CODEX_SANDBOX`, or a universal `AI_AGENT` flag set by the orchestrator — the CLI switches rendering modes automatically. No flag, no extra knowledge required. The agent just runs the command and gets agent-shaped output.

The override still exists for power users: `--format human`, `--format json`, `--format quiet`. But the default is inferred from context, and the agent never has to ask for what it needs.

## Stdout Is a Contract

This one is underappreciated and violated constantly.

Every piece of text that goes to stdout must be parseable data. Every piece of text that goes to stderr can be anything: hints, warnings, progress messages, error details. The separation has always been the intended design of Unix pipelines, but most CLIs violate it freely, writing friendly messages to stdout because that's where the terminal shows output.

For a human running `depot artifacts list | head -5`, the stray "Fetching artifacts from prod registry..." line in the middle of the output is harmless — they can read around it. For an agent parsing that output to extract artifact names, it's a silent corruption.

A well-designed `depot` routes everything that isn't structured data to stderr:

```bash
# stderr (never parsed):
Connecting to prod registry... done
3 artifacts found (filtered from 47 total)

# stdout (always parseable):
api-service-linux-amd64	2.4.1	44367872	2026-06-03T09:22:14+00:00
worker-linux-amd64	2.4.0	39977984	2026-06-01T14:05:31+00:00
frontend-static	1.9.2	8808448	2026-06-06T00:01:09+00:00
```

The agent sees clean data. The human, in a terminal, sees both streams merged and reads the context message. Same binary, correct behaviour for both.

This also means error messages go to stderr and exit with a non-zero code. An agent that gets a non-zero exit can branch immediately. An agent that has to parse stdout to find out whether the command succeeded is spending tokens on what should be a signal.

## The Actionable Error

Most CLI error messages describe what went wrong. Agent-optimised error messages describe what went wrong *and* what to do about it — with the exact command, pre-filled with the correct flags.

When a developer runs `depot artifacts upload ./api-service` and they're not authenticated, a typical CLI says:

```
Error: authentication required
```

A good CLI says:

```
Error: not authenticated. Run `depot auth login --registry prod` to authenticate.
```

The difference sounds trivial. For an agent, it's the difference between a dead end that requires backtracking and reasoning, and a rail that points directly to the next action. The agent reads the error, extracts the command from the message, runs it, and continues. No inference. No tool calls spent on figuring out what `authentication required` means in this context.

The same principle applies to destructive operations that normally require confirmation. `depot artifacts delete api-service-linux-amd64` run interactively might show a confirmation prompt. In agent mode, it fails immediately:

```
Error: destructive operation requires confirmation. Use --yes to proceed without prompt.
```

The agent adds `--yes` and retries. One extra step, but no block, no hang, no waiting forever on a prompt that will never be answered.

## Idempotency by Design

Agents retry. They recover from interruptions. They run the same task twice if the first run's result gets lost in context. A CLI that was designed assuming every command runs once, from a human who checks before proceeding, will produce errors when commands run twice.

The fix is idempotency as a deliberate design choice, not an afterthought.

`depot registries add --name prod --url https://registry.example.com` should succeed silently if the registry already exists. Not with an error. Not with a warning that leaves the agent unsure whether the operation worked. With an `--exist-ok` flag that makes the operation a no-op if the state is already correct:

```bash
depot registries add --name prod --url https://registry.example.com --exist-ok
# exit 0, no output, whether or not prod already existed
```

Upload commands re-commit cleanly on re-run. Create commands check before acting. Delete commands succeed even if the target is already gone — or at minimum return a clear, distinguishable "already deleted" exit code so the agent can treat it as success.

The goal is that any agent workflow built on `depot` can be safely interrupted and resumed from any point without divergence. That's not just good for agents — it's good engineering. But it becomes mandatory the moment agents are in the loop.

## Dry Run Before Anything Moves

For operations that transfer, upload, sync, or delete data, the agent should be able to verify intent before committing. `--dry-run` is the mechanism.

Running `depot sync --source ./build --registry prod --dry-run` should produce:

```
Dry run — no changes will be made
Would upload 4 files (112.4 MB total):
  api-service-linux-amd64  42.3 MB  (new)
  worker-linux-amd64        38.1 MB  (new)
  frontend-static            8.4 MB  (update: 8.1 MB → 8.4 MB)
  config-bundle              0.2 MB  (new)
Would skip 11 files (already current)
```

An agent can verify this output against its expectations, catch unexpected large uploads or missing files, and only then commit to the actual operation. In agent mode, this output should also be machine-readable — structured, not formatted for the eye. The same information, as TSV to stdout, so the agent can parse file counts and sizes programmatically if it needs to reason about them.

## The Next-Command Rail

Every command that kicks off a long-running operation should tell the agent what to run next. Not vaguely — with the exact command, the actual job ID, already filled in.

```
$ depot jobs run --task build --artifact api-service
Job queued: job_8a3f2c1d

To follow progress:
  depot jobs logs job_8a3f2c1d --follow

To check status:
  depot jobs status job_8a3f2c1d
```

This text goes to stderr so it doesn't pollute the parsed output. But an agent reading the terminal will extract `job_8a3f2c1d` from the structured stdout line and immediately have everything it needs for the next step. The IDs are surfaced in stdout in parseable form; the usage hints are in stderr as human guidance.

The agent no longer has to reason about "what do I run to check the status of the job I just created." The CLI answered that question before it was asked, with the correct ID already substituted. Over a multi-step workflow this saves several tool calls and several hundred tokens, and more importantly it eliminates the class of error where an agent guesses a command structure incorrectly.

## The Skill File

All of the above helps agents use a CLI correctly when they know it exists and have already run a few commands. The skill file solves the cold-start problem.

A skill file is a compact, machine-readable reference for the entire command surface of the CLI — one line per command, signature plus flags, grouped by resource, designed to fit in a context window without dominating it. Not prose documentation. Not a man page. A distillation of everything an agent needs to invoke the CLI correctly, without spending tool calls on `--help` discovery.

For `depot`, it looks like this (excerpt):

```
## depot
Artifact registry management CLI.

### artifacts
depot artifacts list [--registry NAME] [--filter QUERY] [-q] [--json]
  List artifacts. -q: one name per line. --json: JSON output.

depot artifacts upload PATH --registry NAME [--tag VERSION] [--exist-ok] [--dry-run] [-y]
  Upload artifact. --exist-ok: no-op if already current. --dry-run: preview only.

depot artifacts delete NAME --registry NAME [--yes] [-q]
  Delete artifact. --yes: skip confirmation.

depot artifacts download NAME --registry NAME [--output DIR] [-q]
  Download artifact to DIR (default: ./). -q: suppress progress.

### jobs
depot jobs run --task TASK [--artifact NAME] [--env KEY=VAL ...] [-q]
  Enqueue a build job. Prints job_id to stdout.

depot jobs status JOB_ID [--json]
  Get job state: queued | running | succeeded | failed.

depot jobs logs JOB_ID [--follow] [--tail N]
  Stream logs. --follow: stream live.

depot jobs cancel JOB_ID [-y]
  Cancel a running job.

### COMMON FLAGS
--format human|agent|json|quiet  (default: auto-detected)
--yes / -y     Skip confirmation prompts
--dry-run      Preview without committing
--exist-ok     Succeed silently if state already matches
--json         Structured JSON to stdout
-q / --quiet   One ID per line to stdout; all else to stderr
```

A team ships this file alongside the binary. Agents install it once — `depot skills add --claude`, for instance — and load it at the start of any session involving `depot`. The HuggingFace team measured a ~30% reduction in tool calls per task just from agents having this upfront context. They don't need to probe the CLI to discover what flags exist. They go straight to the task.

The token cost of loading the file is fixed and paid once. The savings compound across every command in the session. On complex multi-step tasks, the math becomes compelling enough that shipping a skill file should be considered part of shipping the CLI.

## Why This Matters Now

None of the decisions above are technically difficult. Auto-detect the environment variable, render TSV in agent mode, route guidance text to stderr, add `--exist-ok` flags to create operations, print the next command after a long-running operation, write a compact reference file. An experienced CLI author could implement all of this in a few days.

What makes it a design problem rather than an implementation problem is that it requires holding two users in mind simultaneously — a human running commands interactively, and an agent calling the same binary programmatically in a loop. Most CLI design defaults to the human. The human is the primary user, the one who will notice if the output is ugly or the help text is confusing.

The agent is invisible. It doesn't complain. It silently burns tokens on ANSI escape codes, invents command syntax it wasn't sure about, hangs on prompts it can't answer, and produces subtly wrong results that pass the agent's self-check but fail on the actual system. You find out when you read the transcripts, if you read them at all.

The argument for building agent-aware CLIs is not that agents are replacing humans as users. It's that agents are already calling your CLIs, with or without your input, and the design decisions you've already made are shaping whether those calls succeed. Idempotency, clean stdout, actionable errors, auto-detection — none of these hurt human users. They're just good engineering that happens to make the tool composable and predictable.

The gap between a CLI that works for agents and one that doesn't is a handful of deliberate decisions made at design time. After the binary ships, those decisions get expensive to reverse.
