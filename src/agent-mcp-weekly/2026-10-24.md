# 🔌 AI Agent & MCP Weekly — Week of 19 October 2026

## Highlights

The useful signal this week is not another agent loop. It is the infrastructure around the loop: procedural context that can travel between products, state that survives a crashed worker, priorities for competing work, and an operator surface for people supervising several agents. The field is moving from demonstrations that complete a task once to systems that must explain what happened and resume safely when something goes wrong.

## Protocol & portable context

### Agent Skills moves to the AAIF

[Anthropic donated Agent Skills to the Agentic AI Foundation](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation), under the Linux Foundation. Anthropic says that more than 70 platforms, including ChatGPT, Cursor, GitHub Copilot, and VS Code, have integrated the format since its December 2025 publication; it also reports one million published skills and nearly 280 million installations. Those are vendor-reported adoption figures, but the institutional move is the more durable news.

A skill is intentionally simple: a folder containing `SKILL.md`, scripts, and reference material. MCP addresses the boundary where an agent discovers and calls tools; skills address the preceding boundary where an agent receives reusable procedural knowledge. Neither needs to dictate an agent’s internal reasoning, which is why both have a plausible path across competing products. Anthropic’s proposed AAIF roadmap includes versioned releases, a formal proposal process, and security guidance for skill authors and installers. That matters because a skill can carry executable code and instructions: it is a supply-chain object, not merely a prompt fragment.

[Simon Willison noted](https://simonwillison.net/2026/Oct/22/donating-agent-skills/) that MCP already resides at AAIF. Putting its closest companion format in the same neutral home is a credible attempt to make the connective tissue of agent systems vendor-neutral rather than proprietary.

## Frameworks are becoming control planes

### LangGraph adds explicit priority

[LangGraph 1.2.17](https://github.com/langchain-ai/langgraph/releases), released October 24, fixes explicit recursion-limit handling and preserves the caller namespace when `RemoteGraph.stream(subgraphs=True)` is used. The adjacent SDK 0.4.9 adds thread-priority settings, while CLI 0.4.38 adds a `priority` section to `langgraph.json`.

That is operational infrastructure, not model magic. A durable runtime eventually has several tasks competing for capacity, and a scheduler must decide which one deserves service. Priority is an admission-control feature: a human-unblocking request should not necessarily wait behind a batch of long research runs. The namespace fix reaches the same conclusion from another direction—once work crosses remote boundaries, identity and context must remain explicit rather than being accidentally reconstructed.

### CrewAI focuses on bounded execution

[CrewAI 1.15.29](https://github.com/crewAIInc/crewAI/releases), released October 23, promotes `AgentExecutor` out of experimental status and adds offline JEV routing plus a guardrail-evaluation runner. Its release notes also describe tracing conversation routes and public replies in flows, stopping agents from repeating the same tool call, honoring tool failure policies, and refreshing usage budgets for each kickoff.

These features do not improve an LLM’s reasoning. They make failures, costs, and decisions visible and bounded. That is a welcome maturation: an agent framework should increasingly resemble workflow software with model calls embedded in it, not a prompt-composition library that calls a loop “autonomy.”

## Durable agents and human supervision

### Omnara makes the durability boundary explicit

[Omnara](https://github.com/omnara-ai/omnara) was introduced in a [Show HN thread](https://news.ycombinator.com/item?id=50183892) that had **111 points and 34 comments** when checked. Its author describes an architecture in which an agent log is an append-only Postgres event log, workers are stateless, and each worker runs a single model or tool iteration before returning the agent to a Postgres queue. The submission makes the transactional claim plainly: “the model output, its tool calls, usage and the next wakeup are saved together or not at all.”

This is the right question for a long-running agent service: not whether a worker stays alive, but whether a restart can determine exactly which effects committed. The project’s repository likewise describes workers that build context, call models, and run tools only while an agent is taking a turn, allowing one worker to serve many agents. It also separates execution machines from the control plane through an outward-connecting daemon. Postgres is not a universal requirement—single-machine tools can reasonably use local session storage—but a multi-user system needs an explicit durability and authority boundary before it needs another planner.

### Corgi treats attention as a resource

[Corgi](https://corgi.computer/) is a terminal multiplexer built around agent supervision. Its [Show HN launch](https://news.ycombinator.com/item?id=50214373) had **43 points and 6 comments** when checked. The project presents working, needs-you, finished, and unread states; tracks resource usage per workspace; preserves background processes; shows files an agent touched in a replay view; and supports Claude Code, Codex, Pi, and OpenCode.

That separation is sensible. A runtime should own state transitions and authority; the operator interface should make attention and changes legible. A grid of chat transcripts is not supervision. When multiple agents run in parallel, interruption routing, workspace boundaries, and a concise view of what changed become part of the architecture.

## Models and evaluation environments

### Kimi K3.1 Pro reports agentic benchmark results

[Kimi’s K3.1 Pro technical post](https://www.kimi.ai/blog/kimi-k3-1-pro) describes the model as an open-weight, 3T-class release with a one-million-token context window. The vendor reports 65.7% on Terminal-Bench 4.0, compared with 66.4% for Claude Opus 5.5 and 58.2% for GPT-6 Astra; it also reports 61.2% on its internal Kimi Code Bench 3.0 Long-horizon versus 55.95% for K3. These are vendor-reported numbers, not independent replication.

The more useful detail is the training-system description: Kimi says it optimized RL infrastructure, long-context inference, sandbox infrastructure, rollout scheduling, and environment quality checks. Agent benchmark progress is increasingly a story about environments and verifiers, not just a cleverer chat model. Builders should therefore ask whether a model was trained against the constrained, tool-mediated feedback loops their product actually creates—not only compare a headline score.

## What to try next week

Take one workflow that currently depends on a long-running local agent process and map its durable events: input, model response, proposed tool call, tool result, approval decision, usage record, and next wake-up. Then terminate the worker halfway through a run and test whether a restart can state exactly what did and did not happen. If it cannot, improve that boundary before adding a planner, memory layer, or swarm abstraction.
