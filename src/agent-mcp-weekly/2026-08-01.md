## Highlights

This was the week MCP stopped looking like a convenient connection format and started looking like deployable infrastructure. The stable 2026-07-28 specification removes protocol-level sessions, while framework releases independently emphasize explicit failure, durable state, and observability. The common lesson is unglamorous but consequential: agents cannot be reliable if their runtime semantics are hidden inside a chat-shaped blob.

---

## MCP protocol: state belongs in the application

### Stateless MCP is now the baseline

The [2026-07-28 MCP specification](https://github.com/modelcontextprotocol/modelcontextprotocol/releases) is now the stable release. Its [official changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog) removes protocol-level sessions and the `Mcp-Session-Id` header from Streamable HTTP. It also makes `tools/list`, `resources/list`, and `prompts/list` independent of a connection; servers that need cross-call state are directed to use explicit server-minted handles passed as ordinary tool arguments.

That sounds like plumbing, but it is really a decision about who owns state. A server can no longer quietly make a connection itself meaningful. That is convenient for demos and miserable for deployment: retries, load balancing, edge caching, failover, and audits all become entangled with server-side conversational residue. Statelessness instead says that transport is a capability-discovery and invocation boundary, not a container for an agent’s life story. If an agent needs durable state, it should be an explicit resource in the application layer, where it can be versioned, inspected, authorized, and tested.

Simon Willison’s July 31 reflection, “[Stateless MCP has recaptured my interest](https://simonwillison.net/2026/Jul/31/stateless-mcp/),” supplies the practical case. He writes that MCP makes it “much easier to reason about agent capabilities and what might go wrong than with arbitrary command execution in an open network environment.” His Datasette MCP endpoint deliberately provides only three tools—listing databases, fetching a database schema, and executing read-only SQL. The boundary is legible.

This is why “more MCP servers” is not the useful metric. The useful question is whether a server turns ambient access into named, parameterized capabilities. A tool that amounts to “run arbitrary shell” merely moves the old problem behind a JSON schema. A tool that exposes a small query vocabulary, scopes credentials, and makes side effects explicit is infrastructure.

## Frameworks: expose execution, failure, and telemetry

### LangGraph makes the event surface more concrete

[LangGraph 1.2.10](https://github.com/langchain-ai/langgraph/releases), released July 28, adds typed v3 `stream_events` returns and native projections. Its release notes also include work to expose `trace_policy` on `add_node` and then refine that policy surface. These are not end-user flourishes: they treat a running agent as an observable process rather than merely a final answer with theatrical intermediate text.

That distinction matters in production. Operators, users, and evaluators need different views of a run, and projections are a concrete mechanism for presenting the relevant subset without pretending that every internal event is equally useful. If a system cannot make its event stream inspectable, it is difficult to diagnose, evaluate, or safely operate once it becomes long-running.

[CrewAI 1.15.9](https://github.com/crewAIInc/crewAI/releases), released July 30, makes the same point more bluntly. It surfaces tool failures instead of reporting them as success, emits a `FlowFailedEvent` when a flow execution fails, and adds progressive disclosure for skills. The July 31 [1.15.10 release](https://github.com/crewAIInc/crewAI/releases) adds collection of skill-usage events. A workflow that says “success” after a failed tool call is not merely inconvenient; it poisons downstream planning and makes operator telemetry untrustworthy. Failure events and skill-usage events move behavior out of implication and into something an operator can observe.

The pattern across these releases is clear: execution and failure are being pulled out of the model’s implied narrative and into runtime primitives. That is where they belong.

## Agentic patterns: make evaluation replayable

### Smevals separates a run from its judgment

The week’s strongest architectural connection is between stateless MCP and evaluation design. Stateless tool servers remove connection history as a hidden input, making an execution easier to reproduce. But reproducibility only becomes useful when the harness records the rest of the inputs: model, prompt, tool versions, configuration, run artifacts, and grading rules.

That is the bet behind [smevals](https://primeradiant.com/blog/2026/smevals.html), a small evaluation system announced July 31 by Prime Radiant and highlighted by [Simon Willison](https://simonwillison.net/2026/Jul/31/smevals/). It defines an eval as tasks run against configurations; configurations can cover a model, system prompts, model parameters, or agent harnesses; a run records what happened for a task/config pair; and graders use checks to produce grades. The project’s central design choice is explicit: “Runs are treated separately from grading operations.”

That separation is more important than it first appears. It lets a team revise a grader and re-grade recorded runs instead of rerunning an expensive, nondeterministic system. “Did the agent complete the task?” is not enough, because a successful outcome may conceal a brittle route, a lucky retry, or an unauthorized action. An engineering feedback loop needs to identify which configuration produced which artifact and why a grader accepted it.

On Hacker News, the front-page post “Everyone is building LLM routers, we deprecated ours” had **95 points and 51 comments** when checked for this edition. That is a useful counter-signal to the industry’s routing enthusiasm. A model router may reduce cost in a narrow benchmark, but it introduces a second policy engine whose decisions affect quality, safety, and reproducibility. If routing is necessary, its decision belongs in the recorded run configuration and should be evaluated as a component—not treated as invisible infrastructure. The same rule applies to retries, fallback models, and tool-selection heuristics.

## Notable project: constrained capability beats ambient access

### Datasette MCP is a useful small example

Willison’s [Datasette MCP demonstration](https://simonwillison.net/2026/Jul/31/stateless-mcp/) is worth studying precisely because it is not grandiose. Its three-tool interface does not pretend an agent needs unrestricted database power. It makes schema discovery and read-only querying first-class, allowing permissions to be understood without reverse-engineering a shell transcript. For teams connecting agents to business data, that is a better starting point than giving an agent database credentials and hoping the system prompt holds.

Smevals is similarly modest in scope and therefore promising. Its YAML-and-scripts model is a format a team can check into a repository, run in CI, and inspect after an incident. The project explicitly treats prompts and harnesses as configuration variables alongside models. In production, the harness can change behavior at least as much as swapping between closely matched models.

## What to watch next week

Take one MCP integration that retains session-local assumptions—cached discovery results, a per-connection identity, or unrecorded tool configuration—and run it as two independent stateless requests through a proxy or separate worker. Then create a small smevals-style fixture that records the tool schema, arguments, response artifact, and expected side effect for each request.

The goal is not to prove that every agent task is deterministic. It is to expose which state is actually required and force it into an explicit, owned layer. If the system breaks when a connection changes, that is architecture a model upgrade will never fix.
