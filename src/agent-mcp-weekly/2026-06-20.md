## 🔌 MCP Protocol & Servers

The MCP specification team has a draft release candidate in circulation (the spec version page shows changes still being finalized before a formal stable release). Based on the [draft changelog at modelcontextprotocol.io](https://modelcontextprotocol.io/specification/draft/changelog), the changes cluster around three areas: elicitation cleanup, resource handling refinements, and a new formal deprecation lifecycle.

The elicitation change is the most architecturally revealing. The original design had servers issuing a completion signal with an identifier to correlate with the original request — a server-initiated, stateful coordination pattern. The RC removes the `elicitationId` field from URL mode elicitation requests entirely. Servers needing to correlate an elicitation across retries now encode their own identifier in `requestState`. This is deliberate simplification. MCP is pulling back from managing complex stateful interaction patterns and pushing that responsibility to the application layer.

Also in the RC: `structuredContent` now allows any JSON value (with added `$ref` resolution requirements and composition-keyword resource bounds), and a formal lifecycle policy has been introduced establishing a minimum twelve-month deprecation window before features are removed. The lifecycle policy is quietly significant — it's MCP saying "we're done treating this as experimental."

The sharpest outside commentary on what MCP actually is came from Simon Willison, who highlighted a June 19 quote from Sean Lynch: *"The real valuable capability MCP offers over skills/CLI is isolating the auth flow outside of the agent's context window, and potentially out of the harness completely. [...] Maybe the idealized form of MCP is just an auth gateway for the API and nothing else. That'd still be a win."* ([Source →](https://simonwillison.net/2026/Jun/19/sean-lynch/)) This is the most useful framing I've seen. Not tool discovery, not schema description — auth isolation. Credentials stay out of the model's context window; the MCP server holds them. The RC's move to simplify elicitation is consistent with this: the protocol is converging on what it does well, shedding complexity that required stateful agent-to-server negotiation.

The security ecosystem around MCP is accelerating in response to real exposure. Three separate projects appeared on Hacker News this week addressing variations of the same problem: SentinelMCP (an open-source firewall that intercepts MCP tool calls), OpenACA (a security scanner for AI agent stacks — MCPs, skills, and plugins), and a policy gate that runs before coding agent tool calls execute. None of them got meaningful traction by points, but three independent teams solving related problems in one week is a signal. The attack surface that MCP creates — especially for agents with write access to systems — is becoming a recognized and categorized threat class.

Finally, a quiet milestone: GitHub now has MCP Registry listed as a first-class entry in its global platform navigation, alongside Actions and Codespaces. This isn't a product announcement — it appeared without fanfare — but platform navigation real estate signals priority. GitHub is treating MCP as a feature, not an experiment.

This is a framework doing weekly minor bumps across both the core library and the CLI tooling. That pattern means real production usage, real bug reports, and teams shipping fixes fast. Compare to AutoGen, whose latest Python release (v0.7.5) dates to September 30, 2025 — nine months of quiet. AutoGen isn't dead, but it's clearly not the active front.

CrewAI shipped 1.14.8a (an alpha, June 18) with an experimentally interesting addition: `crewai run --definition` for flows. This is a CLI interface for defining and running flows declaratively rather than purely programmatically. The "experimental" label is appropriate — it's not production-ready — but the direction matters. Most agent frameworks have solved "run Python code that orchestrates agents." The harder problem is making that orchestration inspectable and operable by people who aren't Python programmers. A definition-based flow runner is one path there, and the fact that it's arriving as a CLI flag rather than a new object-oriented abstraction is the right instinct. CrewAI also shipped 1.14.7 on June 11 with a practically useful improvement: lazy-loading docling imports to speed up startup. Fast cold starts matter more than people admit — they're the difference between an agent that feels snappy and one that seems to be warming up before it's started.

## 🏗️ Agentic Patterns & Architectures

The week's most substantive community discussion: [Ask HN: Is anyone using the A2A protocol?](https://news.ycombinator.com/item?id=48582679) — 91 points, 41 comments, posted June 18. The answer, broadly, is no. The most analytically detailed comment came from an AI infrastructure developer who concluded that "A2A is not really solving a real-world problem, compared to MCP." The specific architectural critique: A2A assumes the existence of well-defined, stable agent identities — which don't exist in practice. Another commenter quantified it: MCP's SDK monthly download count is roughly 257M compared to A2A's ~10.9M, meaning MCP is downloaded about 24x more than A2A. Enterprise orchestration products (cloud providers, large vendor stacks) have adopted A2A; startup teams building actual agents haven't.

This matters because Google launched A2A with substantial fanfare as a protocol for agent-to-agent communication and delegation. The spec is fine, the SDK exists, the Agent Card concept is coherent. But adoption requires a use case, and the specific use case A2A was designed for — standardized discovery and delegation between agents with stable identities in a mesh — turns out to be less urgent than the use case MCP addresses: connecting a model to a specific tool or service right now. The Sean Lynch framing connects here directly. If MCP's job is auth isolation (getting credentials out of the context window), A2A's job was agent discovery and delegation. But nobody's building distributed agent meshes at scale yet, which means A2A is a protocol for a problem that's real but not yet urgent. The 24x gap isn't because MCP is technically superior — it's because MCP solved a problem developers were actively hitting.

A second pattern worth flagging: context window management for tool-heavy setups is becoming its own tooling category. The concept of loading only the tools relevant to the current task — rather than dumping the full tool manifest into context — is increasingly necessary as MCP server proliferation continues. If you're running an agent with a dozen MCP servers connected, you might have hundreds of tool schemas available. Routing the relevant subset at query time rather than burning tokens on irrelevant schema is architecturally correct. This is a problem that will need solving at scale.

## 🧪 Notable Projects & Demos

Cortex (June 13, HN) is a local-first, encrypted memory store for AI agents, written in Rust, with MCP integration. The combination — local-first, encrypted, Rust — suggests someone who's thought seriously about privacy properties rather than just building fast. Most agent memory systems are cloud-first and unencrypted; they trade privacy for convenience and synchronization. Cortex trades those things back. For privacy-sensitive use cases (legal, medical, personal finance), local-first encrypted memory isn't a niche — it's a requirement.

## 💡 One Thing to Try

Implement tool routing before your tool manifest. Filter your tool list to the subset relevant to the current query before constructing the tool manifest for the model. A simple embedding similarity check between the user's intent and each tool's description can cut your manifest by 60–80% on most requests, reducing both token cost and the cognitive load on the model. This is 20–30 lines of Python with any embedding API, and it's the kind of optimization that's easier to add before you're at scale than after. Do it now while your tool count is manageable.
