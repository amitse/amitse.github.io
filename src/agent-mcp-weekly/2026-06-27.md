## 🔌 MCP Protocol & Servers

The most important thing to understand about the MCP `2026-07-28` draft changelog — [updated June 25](https://modelcontextprotocol.io/specification/draft/changelog) — is that it's not adding features. It's subtracting protocol. This revision takes a meaningful swing at the architectural debt that's accumulated since the original 2024 release, and the dominant theme is *statelessness*.

The headline change: sessions are gone. The `initialize`/`notifications/initialized` handshake that has anchored every MCP session since the beginning has been removed. Instead, every request now carries its protocol version, client identity, and client capabilities inline in `_meta` fields (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientInfo`, `io.modelcontextprotocol/clientCapabilities`). This is a significant conceptual shift. The protocol is moving from "establish a session, then exchange messages" to "every request is self-describing." List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per connection — they're stable, deterministic, and *cacheable*.

That last point deserves emphasis: the spec now *requires* `ttlMs` and `cacheScope` fields on results from list and read operations. Servers must return tools in a deterministic order. `cacheScope` is either `"public"` (result may be cached by shared intermediaries) or `"private"` (result is per-caller). This isn't incidental hygiene — it's an explicit design for LLM prompt cache hit rates. The people writing this spec understand that MCP calls happen inside inference loops where token costs compound.

The other major change is the Multi Round-Trip Request (MRTR) pattern, which replaces the previous mechanism for server-initiated calls like `sampling/createMessage` and `elicitation/create`. Previously, servers could initiate their own requests back to the client mid-operation, which created a two-way dependency that made transport implementations complicated and error-prone. Under MRTR, when a server needs input from the client, it returns an `InputRequiredResult` instead of completing. The client retries the original request after obtaining whatever the server needs. The dependency is one-directional again. This is cleaner to implement and cleaner to reason about.

Two other removals worth noting: the `Mcp-Session-Id` header from Streamable HTTP transport is gone, and OAuth Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents. The OAuth work is particularly interesting — the spec is tightening how credentials are scoped to specific authorization servers, which matters more as MCP deployments move into multi-tenant enterprise contexts.

The `2026-07-28` tag was posted as a Release Candidate in late May. The changelog on the docs site was last modified June 25, indicating active work is still landing before the stable release.

## 🤖 Agent Frameworks

**CrewAI 1.15.0** shipped June 25 ([release notes](https://github.com/crewAIInc/crewAI/releases/tag/1.15.0)), and the list of features tells you where the project is heading: declarative Flow definitions. The release adds `FlowDefinition` as a first-class construct — you can now define a flow as a JSON or YAML document, including agents, crews, `each` loops, conditional `if` expressions, and conversational flow steps. A follow-up alpha `1.15.1a1` landed the next day, adding TUI support for conversational flows and fixing a security issue (SSRF redirect bypass in scrape fetches).

What's architecturally interesting here is the push toward *externalizing* flow topology from Python code. `crewai run` and `crewai flow kickoff` are consolidated into a single command. The direction is toward a model where crew definitions live in configuration files and the framework is a runtime — similar to where Kubernetes landed relative to Docker Compose, where the declarative description becomes the source of truth and the imperative code becomes infrastructure.

The DMN (Decision Model and Notation) mode support is a nod in this direction too. DMN is an OMG standard for decision table modeling. CrewAI adopting it suggests they're targeting workflows that need auditability and formalization — regulated industries, enterprise deployments — not just Python developers building automation scripts.

**LangGraph 1.2.6**, released June 18 (via [releases feed](https://github.com/langchain-ai/langgraph/releases.atom)), is a maintenance release. The notable fix is a regression in 1.2.3 where nested subgraphs weren't properly inheriting parent `checkpoint_ns`, breaking subgraph state isolation. The other substantive fix: stream abort now correctly cancels running subgraphs on v3 streams. Both bugs are the kind that surface specifically in production multi-level agent topologies — not in demos. LangGraph's bug surface increasingly reflects real deployment patterns, which is a sign of where adoption actually is.

**AutoGen** (Microsoft) has had no releases in 2026, with the most recent version being `python-v0.7.5` from September 2025. It remains the most academically-oriented of the major frameworks — the research team continues to publish, but the release cadence has slowed dramatically compared to CrewAI and LangGraph.

## 🏗️ Agentic Patterns & Architectures

The most consequential infrastructure announcement for agent builders this week came from AWS: **Lambda MicroVMs**, [published June 22](https://aws.amazon.com/blogs/aws/run-isolated-sandboxes-with-full-lifecycle-control-aws-lambda-introduces-microvms/), earned 263 points and 146 comments on Hacker News on June 23.

The problem it's solving is well-understood by anyone who's tried to give agents actual execution capability: you need per-session VM-level isolation, sub-second cold start, and the ability to maintain state across user interactions, all without owning virtualization infrastructure. The existing options all fail on at least one dimension. Containers are fast but share a kernel and need significant hardening before you'd put untrusted code in them. Regular Lambda functions are stateless by design. Full VMs take minutes to start. MicroVMs via Firecracker can now do all three: VM-level isolation, sub-second resume from snapshot, and a persistent session that suspends cheaply when idle.

The AWS blog post demonstrates the pattern clearly: you build a Docker image, AWS initializes it and takes a Firecracker memory snapshot, and subsequent launches (and resumes) start from that snapshot. *"My Flask app was already running the moment the launch completed. One API call to get a fully initialized, bootstrapped compute environment."* The idle policy is configurable — suspend after N minutes, auto-resume on next request, billing only during active and suspended (not idle-waiting) states.

This matters for agent builders because the execution sandbox problem has been a persistent bottleneck. Running code generated by users or AI in a shared environment is unsafe. Running it in a clean container per request is expensive. Running it in a VM is slow. MicroVMs collapse the tradeoff. The architectural pattern this enables — one isolated execution environment per conversation, cheap to create, cheap to suspend, fast to resume — is exactly what long-running coding agents need.

The HN thread had substantive discussion about cold start numbers, pricing implications, and the Firecracker lineage (it already powers Lambda and Fargate at scale). The primitive is real and battle-tested — per the announcement, Firecracker has powered over 15 trillion monthly Lambda function invocations.

## 🧪 Notable Projects & Demos

**Workweave Router** ([github.com/workweave/router](https://github.com/workweave/router)) appeared as a Show HN on June 26, earning 144 points and 88 comments. The pitch: a model router that sits in front of your coding agent (Claude Code, Codex, Cursor) and routes each inference request to the cheapest model capable of handling it — saving 40% on token costs in their internal testing. The routing model itself was trained via RL on tens of thousands of agent traces.

The critical technical comment from the thread: coding agents already do model-aware routing internally. Claude Code routes exploration to smaller models and planning to larger ones. A proxy that breaks this control loop — and that doesn't know when a previous attempt on a cheaper model already failed — may optimize locally while degrading the agent's overall feedback loop. The builder acknowledged this and noted they only incur the switching cost once per route decision, but the deeper point stands: routing intelligence that doesn't have access to task-level feedback is making decisions with incomplete information.

The interesting architectural question this surfaces is whether model routing belongs in the agent framework (where it has full task context) or at the API proxy layer (where it can be applied uniformly across any agent). The answer probably depends on whether your agent is model-aware by design. Most current frameworks are.

**Simon Willison** ([simonwillison.net](https://simonwillison.net/)) noted the release of Mozilla's MDN MCP service (not this week's news, but its downstream effects were): he used it as inspiration to convert the `mdn/browser-compat-data` repository — 66MB of browser compatibility data — into a SQLite database queryable via Datasette Lite, with the database hosted on GitHub with open CORS headers. The MCP-to-SQL pipeline pattern he used is increasingly standard: the interesting part is the GitHub Actions workflow (built by Codex Desktop) that force-pushes to an orphan `db` branch to get CDN-served open-CORS hosting for free. More interesting as a workflow demo than as an MCP story.

## 📡 Industry Moves

The launch is structured as a limited preview with the U.S. government involved in vetting initial access — a first. For agent builders, the pricing architecture matters more than the model performance story: the announcement introduced explicit prompt cache breakpoints and a 30-minute minimum cache life. The pattern from the Fable/Mythos situation — high-capability models gated by export controls — continues to define the top of the capability curve as effectively inaccessible for most builders.

## 💡 One Thing to Try

Run the MCP draft changelog through your own servers this week and check for `ttlMs`/`cacheScope` compliance on your list endpoints. The upcoming `2026-07-28` stable release will require these fields on `tools/list`, `resources/list`, and `resources/read` responses. Most existing server implementations don't return them. The `cacheScope` field is either `"public"` (result may be cached by shared intermediaries) or `"private"` (result is per-caller only). Getting this right now, before the stable release lands and clients start relying on it, is less painful than retrofitting it after breakage. The draft spec is at [modelcontextprotocol.io/specification/draft/changelog](https://modelcontextprotocol.io/specification/draft/changelog).

## 📊 TL;DR

The MCP draft changelog is the most architecturally significant MCP update since the 2025-11-25 stable release — it strips session state from the protocol entirely, mandates caching hints on every list operation, and rewires server-to-client communication through a one-way MRTR pattern. AWS Lambda MicroVMs solves the agent execution sandbox problem cleanly: VM isolation, Firecracker performance, stateful sessions, no infrastructure to own. CrewAI 1.15.0 is pushing declarative flow definitions as the primary authoring surface, with the framework increasingly resembling a runtime for externalized agent topology rather than a Python library. The week's underlying tension: the models at the frontier (GPT-5.6 Sol, Mythos) are increasingly access-controlled in ways that make building reliably on them harder, which makes the infrastructure and tooling layer — where MicroVMs and smarter caching live — matter proportionally more.
