## 💡 How People Are Using It

Simon Willison's [sqlite-utils 4.0rc2 post](https://simonwillison.net/2026/Jul/5/sqlite-utils-fable/) from July 5 is the most concrete cost accounting of an AI-assisted software project published this year. He gave Fable the prompt "Final review before shipping a stable 4.0 release — very important to spot any last minute things that would be a breaking change if we fix them later," and Fable returned a report with five release-blocker bugs he hadn't encountered himself. The whole project ran while he was at the Half Moon Bay 4th of July parade, checking in from his phone to hand Fable the next task. Total estimated cost: $149.25 at unsubsidized API rates — which is what it will cost from tomorrow. He used `uvx agentsview` inside the existing session to calculate costs retroactively. The post is honest about what it felt like: "I have several other major Fable-driven projects on the go right now as well, with the goal of hitting 100% on that Fable bar just in time for the price increase." That's not irrational — it's optimal behavior given the incentives.

The fly.io post [Building Agents That Don't Break Themselves](https://fly.io/blog/building-agents-that-dont-break-themselves/) makes a structural point that should be read by everyone building multi-user agent platforms: where your agent runs and where it runs code are two entirely separate concerns. The post profiles two real fly.io implementations — SpriteDoc (an internal troubleshooting agent built on Pi) and Hermes Agent from Nous Research — both of which separate the long-lived agent loop from the throwaway execution sandbox. The security detail that deserves attention: SpriteDoc injects user credentials into the sandbox environment for the duration of a single command and removes them when the command returns. The token is never at rest. That's the shape multi-user agent authentication should take, and it's not the default most people build toward.

The arxiv paper [Does Code Cleanliness Affect Coding Agents?](https://arxiv.org/abs/2605.20049) (34 points, 13 comments on [HN](https://news.ycombinator.com/item?id=48798815), July 5) ran 660 Claude Code trials across six matched repository pairs — same architecture, same dependencies, same external behavior, differing on static analysis violations and cognitive complexity. The result: code cleanliness doesn't change pass rate. It does change the operational footprint: agents working on cleaner code use 7–8% fewer tokens and reduce file revisitations by 34%. The conclusion is practical and counter to the popular "AI doesn't care about code quality" narrative: clean code isn't a courtesy to future maintainers, it's a constraint on how efficiently an agent can work. Messy code means more backtracking, and at API scale, backtracking costs money.

## 🔥 Discourse & Drama

Armin Ronacher's [Better Models: Worse Tools](https://lucumr.pocoo.org/2026/7/4/better-models-worse-tools/) (July 4) is the most technically specific critique of a flagship AI capability to surface in months, and it deserves close reading. The setup: a bug report in Pi (his agent framework) revealed that Opus 4.8 and Sonnet 5 — the SOTA models in the current Claude family — sometimes emit extra, invented fields when calling Pi's edit tool. The tool call itself is often correct; the model adds trailing keys including `requireUnique`, `oldText2`, `in_file`, `cost`, and even `event.0.additionalProperties` inside the edit object. What makes this genuinely troubling is the directionality: *older* Claude models don't do this. This is regression, not rough edges in a new capability.

Ronacher's hypothesis about causation is the part worth sitting with: *"Modern Anthropic models are most likely different because their post-training includes Claude Code or a harness that looks very similar... Claude Code's own tools are comparatively flat... Looking at Claude Code's client is very instructive: it contains retry paths for malformed tool use, parameter aliases, type coercions, Unicode repairs and filtering of unknown keys. In other words, Anthropic's own client appears to expect and accept a fair amount of slop and repairs it, mostly silently."* The implication is that training on a permissive harness taught the model that adding random keys is fine — because in Claude Code's own environment, it is. The model learned the wrong thing from the right training signal.

This connects directly to Willison's post about Fable's judgment. The Claude Code team's advice to let Fable use its own judgment works when you're operating in Anthropic's preferred harness. The moment you bring a different tool schema — one with nested arrays, strict validation, no forgiveness for trailing keys — you're outside the distribution the model optimized for. The gap between "what Claude can do" and "what Claude does reliably in arbitrary environments" is real and widening as the harness assumptions accumulate.

The Zuckerberg admission ([99 points, 247 comments on HN](https://news.ycombinator.com/item?id=48767058)) that AI agent development is "going slower than expected" generated one of the more substantive HN threads this week. The comments split between people pointing to coordination overhead ("reviewing code is becoming the bottleneck"), infrastructure immaturity, and the fundamental challenge of agents operating in systems with real-world state. The structural tension: review is a bottleneck and a safeguard simultaneously, and treating it purely as friction to be eliminated has costs that arrive on a delay.
