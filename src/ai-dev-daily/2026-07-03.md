## 🚀 Releases & Changelogs

[**VS Code 1.127**](https://code.visualstudio.com/updates/v1_127) shipped on July 1 with the agents-everywhere arc reaching its logical endpoint: browser tools are now generally available, meaning agents can open pages, take screenshots, and click through UI to validate their own output. For anyone building web applications, this closes a loop that's been quietly broken — agents that write front-end code but can't see what it renders. The release also ships a redesigned Agents window with session grouping, drag-and-drop reordering, and the ability to collapse groups. "The sessions list can grow quickly and become hard to scan" when running several sessions in parallel, as the release notes acknowledge without apology. The VS Code team is designing for multi-agent parallel work as the normal case.

Two other additions in 1.127 are subtle but operationally important. **Chat input banners** surface failing CI checks and incoming PR review comments directly in the conversation panel — not a badge, but a contextual card with a single action: fix it with an agent or reveal the details. The gap between "agent opens a PR" and "you notice the checks failed" just got shorter. And **editor gutter feedback** lets you hover any line, click an Add Feedback glyph, and drop a comment directly to the agent — more precise than describing a code location in prose and then hoping the model finds the right line.

## 🛠️ Tool Updates

### GitHub Copilot / Coding Agent

GitHub compressed four significant changes into July 1–2. First: [**Copilot Vision is generally available**](https://github.blog/changelog/2026-07-01-copilot-vision-is-generally-available/) on all plans, including Free. JPEG, PNG, GIF, WebP, and PDF attachments now work across VS Code, github.com, and the CLI. Previously, Business and Enterprise customers needed a policy flag toggled at the org level; that requirement is gone. The changelog's phrasing is deliberate — "no policy changes or admin actions are required to turn it on" — signaling that the friction-to-default threshold for vision is now zero across the entire subscriber base.

The more structurally interesting move: [**Kimi K2.7 Code is now in the Copilot model picker**](https://github.blog/changelog/2026-07-01-kimi-k2-7-is-now-available-in-github-copilot/), explicitly labeled as "the first open-weight model offered as a selectable option." It's hosted by GitHub on Azure and billed at provider list pricing — almost certainly cheaper than the proprietary tiers. Rolling out to Pro, Pro+, and Max plans first; off by default for Business and Enterprise pending admin enablement. This is a quiet but significant reframing: the Copilot model picker was previously a curated set of Microsoft-aligned proprietary models. Letting an open-weight model in positions it as a genuine marketplace. Combined with the Models playground dying on July 30, the direction is clear — GitHub is consolidating AI model access into Copilot and away from standalone infrastructure.

On the [**GitHub Models full retirement**](https://github.blog/changelog/2026-07-01-github-models-is-being-fully-retired-on-july-30-2026/): July 30 is the hard date. The playground, model catalog, inference API, and BYOK endpoints all go dark. Brownouts on July 16 and July 23 will serve as forced migration rehearsals. "Unlike the first step in June, this change applies to everyone, including existing customers with active usage." Azure AI Foundry is the recommended migration target for raw model access; Copilot is the pitch for GitHub-native workflows. The clock is running.

[**Copilot agent session streaming**](https://github.blog/changelog/2026-07-02-copilot-agent-session-streaming-is-now-in-public-preview/) hit public preview on July 2 for Enterprise Cloud customers with managed users. All Copilot client activity — prompts, responses, tool calls — can now stream to a SIEM or Microsoft Purview. The REST API variant covers the last 48 hours on demand. This is the enterprise audit trail that large organizations need before they can greenlight real agent deployment; it's also a signal that GitHub is expecting significant agent session volume at scale.

### Claude Code CLI

After last week's Sonnet 5 promotion to default model in v2.1.197, the pace didn't slow. **v2.1.198** (July 1) promoted background subagents from gradual rollout to the actual default: Claude now keeps working while subagents run in parallel, notified via hook when they complete (`agent_needs_input` / `agent_completed`). Same release shipped Claude in Chrome as generally available, a `/dataviz` skill for chart and dashboard design guidance with a runnable color-palette validator, and an important behavioral change: background agents launched from `claude agents` now automatically commit, push, and open a draft PR when they finish code work in a worktree. That removes what was previously a manual handoff — the agent no longer stops to ask. Gateway also added Claude Platform on AWS (`anthropicAws`) as an upstream provider, with model-not-found responses advancing the failover chain instead of terminating it — useful for enterprises with AWS procurement requirements.

**v2.1.199** (July 2) is a hardening release, and the length of its changelog is an accurate indicator of how much operational infrastructure background agents require. Stacked slash-skill invocations now work up to five leading skills in one command (`/skill-a /skill-b do XYZ`). SSL certificate errors from TLS-inspecting proxies now fail immediately with a fix hint instead of burning retries before surfacing the problem. Streaming responses that hit mid-stream server errors now keep the partial output with a notice rather than silently discarding it. Subagents cut off by rate limits now return partial work to the parent rather than failing silently. The Linux background-agent daemon fix is buried in the list but striking: a corrupted worker record left by an unclean shutdown was killing every running agent every ~50 seconds. That kind of bug surfaces only when background agents are actually running at scale.

Worth noting from earlier in the week: v2.1.196 (June 29) added a meaningful MCP security fix — `claude mcp list/get` no longer auto-spawns `.mcp.json` servers that a repo self-approved via a committed `.claude/settings.json`. Untrusted workspaces now show a Pending approval indicator. In an environment where repositories can ship with bundled MCP server definitions, that's an important guardrail that was missing.

## 💡 How People Are Using It

The most technically interesting community tool this week: Simon Willison published [**llm-coding-agent 0.1a0**](https://simonwillison.net/2026/Jul/2/llm-coding-agent/) on July 2, a coding agent built on his `llm` Python library — and the meta-story is as interesting as the release. He built it using Claude Code: first prompt for a spec, second prompt for red/green TDD across a series of commits. The resulting agent shipped a `CodingAgent` Python API that Willison says he "didn't ask for but I'm delighted to see implemented." The `llm` library started as a CLI for querying models; it has quietly evolved into what Willison now calls "more of an agent framework." This release is the proof-of-concept moment for that framing. Available via `uvx --prerelease=allow --with llm-coding-agent llm code`.

The short-leash argument also found an audience. Greg Slepak's [**"The Short Leash AI Coding Method For Beating Fable"**](https://blog.okturtles.org/2026/07/short-leash-ai-method/) — which argues expert developers should review every diff, deny permissions whenever the agent starts drifting, and treat AI-assisted PRs like peer code review — generated significant community engagement on HN. Slepak writes from the position of someone who maintains security-critical software and has built internal AI review tooling; the post is grounded in domain-specific threat modeling rather than generic skepticism. The HN response was substantive, including pushback from commenters who argued the "short leash" is a sign of insufficient up-front specification rather than a best practice.

## 🔥 Discourse & Drama

The most-commented AI dev thread this week is the Slepak methodology argument. [**"The short leash AI coding method for beating Fable"**](https://blog.okturtles.org/2026/07/short-leash-ai-method/) hit 61 points and 61 comments on [HN](https://news.ycombinator.com/item?id=48766026) — a point-for-comment ratio that signals genuine argument rather than passive upvoting. Slepak's position: expert developers who outclass the model in their domain should review every diff, deny permissions whenever the agent starts drifting, and treat every AI-assisted PR as a peer code review of someone else's work. The target is "vibe engineering" — 12 parallel agents while you sip coffee — which he argues makes it impossible to maintain real understanding of your own codebase.

The HN response was substantive and largely pushback. "This 'short leash' seems like more of a crutch to me, and a sign of not giving the AI enough detail on the problem to begin with." "I feel like OP is still in the year 2025 — except that said AI can now themselves use your software and find and fix bugs themselves." Both critiques have force for well-saturated domains where model reliability is high and speed is the binding constraint. Slepak's case holds for security-critical systems in niche areas with thin training data, where a single wrong diff is expensive and the model's reliability ceiling is lower. The structural tension isn't resolvable — both positions are correct for different problem shapes. What's notable is the timing: this debate landed the same week Claude Code made background subagents the default and VS Code shipped browser-agent validation as GA. The industry's infrastructure momentum is toward trust. The argument for oversight is being made from an increasingly downstream position.
