## 🚀 Releases & Changelogs

**[Copilot SDK — Generally Available](https://github.blog/changelog/2026-06-02-copilot-sdk-is-now-generally-available)** *(GitHub Changelog, June 2)*

The GitHub Copilot SDK is now GA across six languages: Node/TypeScript, Python, Go, .NET, Rust, and Java (the last two new at GA). The pitch is direct — embed Copilot's agentic engine into your own apps without rebuilding the orchestration layer. Key capabilities include custom tool registration, MCP server connectivity, streaming multi-turn sessions, and file-editing primitives. This matters because it's the first time GitHub has offered the *runtime* behind Copilot as an embeddable component, not just an API for completions. Since entering public preview, it's been used to build CI/CD assistants, internal dev tools, and customer-facing AI features. The door to "Copilot-inside-your-product" is now open with production SLAs behind it.

**[GitHub Copilot CLI — Rubber Duck, Prompt Scheduling, Voice Input](https://github.blog/changelog/2026-06-02-copilot-cli-improved-ui-rubber-duck-prompt-scheduling-and-voice-input)** *(GitHub Changelog, June 2)*

Copilot CLI got its biggest update since launch, shipping three new modes plus an experimental terminal redesign. **Rubber duck** mode lets you explain a problem to Copilot and get back a structured second opinion — less autocomplete, more pair-review. **Prompt scheduling** via `/every` and `/after` lets you fire off prompts on a timer or delay, useful for long-running agentic work. **Voice input** is now GA. The experimental `--tui` now has tabs for Issues, Pull Requests, and Gists directly in the CLI. The redesign also claims better accessibility — narrower terminals no longer truncate critical output. Together, this positions Copilot CLI as a full-time terminal companion, not just an extension of chat.

**[Cloud and Local Sandboxes for GitHub Copilot — Public Preview](https://github.blog/changelog/2026-06-02-cloud-and-local-sandboxes-for-github-copilot-now-in-public-preview)** *(GitHub Changelog, June 2)*

Copilot can now run code, tools, and commands inside isolated sandboxes — locally or in GitHub-hosted cloud environments. This is the infrastructure answer to the obvious question: *if Copilot can modify files and run commands, how do enterprises contain blast radius?* The answer is environment policies, consistent identity, and sandboxed tool execution. Local sandboxes give you the control; cloud sandboxes give you stateless, parallelizable agent runs hosted by GitHub. This is agentic development starting to look like agentic operations — with the same governance controls you'd want before handing an agent keys to your infra.

**[Extend GitHub with Agent Apps](https://github.blog/changelog/2026-06-02-extend-github-with-agent-apps)** *(GitHub Changelog, June 2)*

Third-party agents are now installable from the GitHub Marketplace and embedded directly into GitHub workflows. The first wave includes partners like Amplitude, Bright Security, Endor Labs, LaunchDarkly, Miro, Sonar, PagerDuty, Packfiles, and Octopus Deploy. Entry points are issue assignment, PR @-mentions, and the new Agents UI. GitHub has opened a waitlist for anyone building agent apps for future access. This is GitHub's answer to the MCP marketplace problem: instead of a registry of tool servers, it's a registry of *deployed agents with GitHub identity*. The integration depth is notable — these aren't webhooks in disguise, they're first-class actors in GitHub's workflow graph.

**[MAI-Code-1-Flash — Microsoft's First Coding Model](https://microsoft.ai/news/introducingmai-code-1-flash/)** *(Microsoft AI, June 2 — 427 points, ~184 comments on HN)*

Microsoft shipped its first in-house coding model, MAI-Code-1-Flash, a 137B parameter MoE model (5B active parameters). Per the model card, it scores 51% on SWE-Bench Pro and positions itself against Claude Haiku 4.5. The HN community was quick to contextualise: one commenter noted that Qwen3.6-35B-A3B scores 49.5% on SWE-Bench Pro with 75% fewer total parameters and 98% fewer active parameters, making the MAI-Code comparison to Haiku look generous. A separate model, MAI-Thinking-1, also shipped at Build and targets competition with Claude Sonnet. The honest read: this is Microsoft proving it *can* ship its own models, not that it's leading the field. The geopolitical subtext — Microsoft reducing OpenAI dependency — is the more durable signal.

> "It's a smaller (137B) model that competes with Haiku, but it's basically the performance of Qwen3.6-35B-A3B which is 75% smaller and 98% smaller in terms of active parameters." — HN commenter, on MAI-Code-1-Flash

**[Claude Code v2.1.161](https://github.com/anthropics/claude-code/releases/tag/v2.1.161)** *(Anthropic, June 2)*

Two useful additions in the latest Claude Code release: `OTEL_RESOURCE_ATTRIBUTES` values are now included as labels on metric datapoints — meaning you can slice usage metrics by custom dimensions like team, repo, or environment, which matters for enterprise cost tracking. The `claude agents` TUI row now shows a `done/total` counter before the detail when work is fanned out, and peek surfaces the longest-running item. Small ergonomic wins for teams running multi-agent workflows with meaningful parallelism.

**[Claude Code v2.1.160 — Security Hardening](https://github.com/anthropics/claude-code/releases/tag/v2.1.160)** *(Anthropic, June 2)*

This one is worth calling out specifically: Anthropic added a confirmation prompt before Claude Code writes to shell startup files (`.zshenv`, `.zlogin`, `.bash_login`) and `~/.config/git/`. The previous behaviour — silently writing to these files — could lead to unintended command execution on next shell startup. `acceptEdits` mode also now prompts before writing build-tool config files that grant code execution (`.npmrc`, and others). This is an agentic safety boundary being drawn more carefully: writing to files that cause *future* code execution is meaningfully different from writing to a source file, and Claude Code now treats it that way.

**[VS Code 1.122](https://code.visualstudio.com/updates/v1_122)** *(Microsoft, May 28)*

The headline in 1.122 is **usage-based billing for Copilot** — the model picker now shows per-token costs so users can make informed choices. The Agents window continues to mature: session hover details, improved local harness support in Insiders, and richer OpenTelemetry signals (a canonical `github.copilot.*` attribute namespace) that match CLI conventions. Air-gapped BYOK is now supported — use your own models offline. Integrated browser gains device emulation for responsive testing. VS Code Live at MS Build was scheduled for June 3; expect insiders updates to follow.

## 🔥 Discourse & Drama

**[GitHub Copilot switches to usage-based billing — developers react](https://www.reddit.com/r/GithubCopilot)** *(referenced in HN thread for MAI-Code-1-Flash, 427 points)*

The most visceral reaction to Build 2026 has nothing to do with new features. GitHub Copilot moved from per-request to per-token billing — and developers are furious. One HN commenter wrote: *"GitHub Copilot had competitive pricing until yesterday when they changed from per-request to one of the most expensive per-token quotas. I have since changed to DeepSeek Flash on high which is Sonnet+ level for almost free."* The r/GithubCopilot subreddit was described in the same thread as "burning." This is the tension at the heart of all the Build announcements: GitHub is building enterprise infrastructure (SDK, sandboxes, agent apps) while the developer-tier users who made Copilot's brand are feeling squeezed out. The SDK GA is aimed at companies who can justify per-token economics; the individual developer is being told to recalculate.

**[1-Click GitHub Token Stealing via a VSCode Bug](https://blog.ammaraskar.com/github-token-stealing/)** *(169 points, ~23 comments on HN, published June 2)*

Security researcher Ammar Askar disclosed a VSCode webview vulnerability that allowed an attacker to steal a GitHub OAuth token — with full read/write access to all repos, public and private — via a single link click. The bug exploited a design tension in VSCode's webview security model: to keep keyboard shortcuts like Ctrl+Shift+P working inside iframes, VSCode routes keystrokes across the webview boundary. A malicious extension or crafted input could exploit this message-passing path to exfiltrate the token that `github.dev` posts to itself at startup. That token is unscoped to the specific repo — it's your full GitHub credential. The issue has been patched, and VSCode handled the disclosure well (the article's "What VSCode Did Well" section is worth reading). But the structural tension — rich Electron app + OAuth token + untrusted content rendering — won't be fully resolved until the architecture changes.

> "Just by clicking a link, it's possible for an attacker to steal a GitHub token that can read and write to your repos, including private ones."

This disclosure lands on the same day GitHub ships sandboxed agents and an embeddable agent SDK — tools that will also need OAuth tokens and run in browser contexts. The security model for agentic tooling is still being written, and this bug is a reminder of how high the stakes are.

The common thread is that AI dev tooling is graduating from "feature" to "infrastructure" faster than the trust, pricing, and security models can keep up.
